# M09: Jackage self-hosting

These scenarios are product test designs, not executed tests.

## SELF-001: Realize own environment

Given: The reviewed Jackage recipe and lock exist.

When: B0 realizes its toolchain.

Then: All required tools come from declared verified inputs.

Required platform roles: host.

## SELF-002: Build stage one

Given: B0 executes the locked Jackage build.

When: The build completes.

Then: A functional B1 client and its provenance exist.

Required platform roles: host.

## SELF-003: Build stage two

Given: B1 starts from fresh work and output directories.

When: It rebuilds Jackage without result-cache reuse.

Then: B2 produces the declared comparable artifacts.

Required platform roles: host.

## SELF-004: Compare stages

Given: B1 and B2 use equivalent declared recipes and toolchains.

When: Artifact digests are compared.

Then: Equal payloads pass and unequal payloads produce a reproducibility failure.

Required platform roles: host.

## SELF-005: Keep compiler exact

Given: A newer master build appears online.

When: Self-hosted builds run in locked mode.

Then: They retain the supplied pin until an authorized lock change.

Required platform roles: host.

## SELF-006: Bootstrap without Jackage

Given: A clean test environment lacks installed jckg.

When: The documented bootstrap runs.

Then: It produces or verifies the first client from declared external inputs.

Required platform roles: host.

## SELF-007: Preserve primary source

Given: A Linux self-hosted build uses the Windows checkout snapshot.

When: The action runs.

Then: No independently maintained ~/src checkout is required.

Required platform roles: host.

## SELF-008: Install self package

Given: A local signed channel advertises the Jackage build.

When: Install and jckgx execute that package.

Then: Both clients run through the same verification path.

Required platform roles: host.
